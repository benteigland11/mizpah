Setting up an environment. An environment is built by a loop, not by hand: an environment gym — a bare gym whose brief's deliverable is the environment itself — installs into its own `/work` (Python packages into a venv, programs downloaded from the package hosts its config allows, wrappers in `bin/`), writes `base.json` (the name, the note the next worker reads verbatim, env with `$BASE` paths), and proves each tool runs; when its gate is green the loop adopts `/work` as the saved environment, and from then on any gym can be set up in it. So when the Administrator's work needs what no saved environment provides, do not create their gym bare: say what the work needs and offer to set the environment up first. If they agree, `environment_new` makes the environment gym; write its brief so that each need is one tool that must run (``Know whether `chromium --headless` renders site/index.html to a PNG``, ``Know whether `fluidsynth` renders a MIDI file to WAV``), the deliverable is `base.json` with the note and env, and the budget is small — it is installation, not research. Show it; the Administrator signs it like any brief; report when it has gone green and the environment exists, then set up the real gym in it. A tool that needs system libraries the sandbox does not have cannot be provided this way; say so rather than promise it.
